## 1. 채점이 3층으로 나뉘는 이유

"협력 층위 L0~L4"라는 하나의 결론이 나오기까지 **서로 다른 성격의 채점 3개**가 관여한다.
셋을 구분하지 않으면 결과가 이상할 때 어디를 고쳐야 할지 알 수 없다.

| 층 | 무엇을 재는가 | 누가 재는가 | 산출물 | 어디에 쓰이는가 |
|---|---|---|---|---|
| **1층 산출물 품질** | 답이 얼마나 좋은가 | A1=코드 / A2·A4=LLM judge | A1: 0~1 점수 / A2·A4: 1~5 등급 | Q3 (집단 우위) |
| **2층 발화 기능** | 각 발화가 무슨 역할인가 | LLM 코더 | 발화별 코드 + 참조 | Q1, Q2, Q4 |
| **3층 협력 층위** | 결국 어떤 협력인가 | 결정 트리(코드) | L0~L4 | 최종 결과 |

1층과 2층은 **독립적으로** 산출되고, 3층이 둘을 합쳐 판정한다.
따라서 결과가 이상하면 `stopped_at`(병목)을 보고 어느 층을 의심할지 정한다.

- `Q1`/`Q2`에서 막힘 → **2층(태깅)** 또는 시나리오 설계 문제
- `Q3`에서 막힘 → **1층(산출물 채점)** 또는 시나리오 난이도 문제
- `Q4`에서 막힘 → 1층·2층 양쪽

## 2. 무엇을 채점하는가 — 채점 대상 정의

**가장 먼저 정해야 하는 것이 "채점 대상"이다.** 같은 대화라도 무엇을 채점하느냐에 따라
점수가 완전히 달라지기 때문이다.

### 규칙

| 조건 | 채점 대상 |
|---|---|
| 단독(solo) | `run_solo()`가 반환한 `output` 전체 |
| 2-agent | `log["final_output"]` — 대화가 끝난 뒤 최종 결론만 따로 요청해 받은 텍스트 |

`final_output`이 없는 옛 로그는 **마지막 두 턴(양쪽 화자 각 1턴)을 이어 붙인 것**을 쓴다.
구현: `agents.group_output_text()`

### 왜 대화 전체를 채점하지 않는가

대화 전체를 채점하면 (a) 길이가 단독 조건의 몇 배가 되어 길이 편향이 생기고,
(b) 도중에 나온 오답과 폐기된 안이 함께 채점되며, (c) 화자 표기 때문에 블라인드가 깨진다.
**단독 조건과 그룹 조건이 같은 형태의 산출물이어야 비교가 성립한다.**

### 블라인드 처리

judge에게 넘기기 전 `scoring.anonymize_output()`이 `alpha:` / `beta:` 표기와
이름 언급을 지운다. 이 처리가 없으면 judge가 한 줄만 보고 그룹 조건임을 알아차려
**'블라인드 채점'이 이름뿐이 된다.**

## 3. A1 채점: 체크리스트

A1(정보통합)은 정답이 존재하므로 **LLM 없이 코드로 결정론적으로** 채점한다.
같은 산출물은 몇 번을 돌려도 같은 점수가 나온다.

### 3-1. 계산식

시나리오의 `scoring.checklist` 항목 각각에 대해:

```
항목 점수 = (산출물에 등장한 토큰 수) / (항목의 전체 토큰 수)
최종 점수 = 항목 점수들의 평균                            → 0.0 ~ 1.0
```

- **토큰** = 체크리스트 항목을 공백으로 쪼갠 조각
- 비교 전에 양쪽 모두 **정규화**한다: 소문자화 + NFKC(전각→반각) + 공백·구두점 제거

### 3-2. 정규화 예시

| 원문 | 정규화 결과 |
|---|---|
| `19:00`, `19 : 00`, `１９：００` | `1900` |
| `panel-3`, `panel 3` | `panel3` |
| `B실`, `B 실`, `b실` | `b실` |

### 3-3. 채점 예시

**짧은 키워드 (A1_simple_meeting)**

```
checklist = ["수요일", "19:00", "B실"]
산출물    = "수요일 19:00에 B실을 예약하는 것이 좋겠습니다."

수요일 → 1토큰 중 1개 = 1.0
19:00  → 1토큰 중 1개 = 1.0    ("1900"이 산출물 정규화 결과에 포함됨)
B실    → 1토큰 중 1개 = 1.0
                       평균 = 1.000
```

**문장형 항목 (A1_complex_power_outage)**

```
checklist = ["C동 전기실 panel-3 과부하 차단", "대형 장비 동시 기동", "D10", "D14"]
산출물    = "최종 원인은 C동 전기실의 panel-3 차단기가 과부하로 내려간 것입니다.
            3층 실험실에서 대형 장비를 동시에 기동한 것이 방아쇠였습니다. 근거: D10, D14."

"C동 전기실 panel-3 과부하 차단" → 5토큰[c동/전기실/panel3/과부하/차단] 전부 등장 = 1.0
"대형 장비 동시 기동"            → 4토큰 전부 등장                          = 1.0
"D10"                            → 1.0
"D14"                            → 1.0
                                                                     평균 = 1.000
```

**부분 점수가 왜 필요한가.** 항목 전체가 토씨 하나 안 틀리고 일치해야 1점을 준다면,
`"C동 전기실 panel-3 과부하 차단"` 같은 문장형 항목은 LLM이 맞힐 확률이 사실상 0이다.
그러면 A1_complex의 그룹·단독 점수가 **구조적으로 전부 0에 수렴**하고,
Q3(집단 우위)이 영원히 실패해 **판정이 항상 L2로 고정된다.** 실험 자체가 무의미해진다.

### 3-4. 사용법

```python
from coop_pipeline.scoring import score_a1, score_a1_detail

score_a1(output, checklist)                  # 0.0 ~ 1.0
score_a1(output, checklist, partial=False)   # 엄격 모드: 항목 전부 일치해야 1점

score_a1_detail(output, checklist)
# {"score": 0.75, "per_item": {"수요일": 1.0, "19:00": 1.0, "B실": 0.0}}
```

`score_a1_detail()`로 **어느 항목에서 점수를 잃었는지** 확인하고 체크리스트를 개선한다.

### 3-5. 체크리스트를 쓸 때의 권장 사항

- 짧은 키워드가 가장 안전하다 (`"수요일"`, `"B실"`).
- 문장형이어도 동작하지만, **불필요한 조사·수식어를 넣지 말 것.**
  `"C동 전기실 panel-3 과부하 차단"` (좋음) vs `"C동의 전기실에 있는 panel-3이 과부하로 차단됨"` (나쁨)
- 표기가 여러 가지인 값은 **가장 지문에 가까운 형태**로 쓴다.
  지문이 `19:00`이면 `"19:00"`으로. LLM은 지문 표기를 따라가는 경향이 있다.

## 4. A2/A4 채점: LLM judge 등급

A2(의견수렴)/A4(창의공동생성)는 정답이 없으므로 LLM judge가 **1~5점**을 매긴다.

### 4-1. 등급 앵커

| 등급 | 기준 |
|---|---|
| 1 | 한쪽 입장/관점만 반영 |
| 2 | 절충 시도했으나 피상적 |
| 3 | 핵심 논거를 균형있게 반영 |
| 4 | 논거 간 트레이드오프까지 조율 |
| 5 | 새로운 대안까지 제시 |

### 4-2. 상한 규칙 (등급 인플레이션 방지)

앵커만으로는 judge가 3~4점에 몰린다. 아래 규칙으로 상한을 건다.

- 지문의 제약(예산, 개수, 기한 등)을 **위반**한 산출물 → 최대 **3점**
- 결론을 하나로 확정하지 않고 여러 안을 **나열만** 한 산출물 → 최대 **2점**
- 확신이 서지 않으면 **낮은 쪽**을 준다

### 4-3. 통제 조건

| 항목 | 설정 | 이유 |
|---|---|---|
| 블라인드 | 단독/그룹 여부를 프롬프트에 노출하지 않고, 화자 표기도 제거 | 조건을 알면 judge가 그룹에 후한 점수를 준다 |
| 생성 모델과 분리 | 생성=gemini/llama, 판정=claude | 같은 모델이면 자기 산출물을 선호한다(self-preference bias) |
| temperature | `0` | 채점은 재현 가능해야 한다 |
| 출력 형식 | JSON 강제 + 파싱 실패 시 3회 재시도 | 형식 오류로 배치 전체가 죽는 것을 막는다 |

### 4-4. 사용법

```python
from coop_pipeline.scoring import score_a2_a4, score_a2_a4_detail

score_a2_a4(output, api_key)          # 4
score_a2_a4_detail(output, api_key)   # {"grade": 4, "reason": "..."}
```

**`_detail`을 써서 `reason`을 반드시 남길 것.** 등급만 있으면 인간 채점자와 갈렸을 때
왜 갈렸는지 알 수 없다.

### 4-5. 이 척도의 알려진 약점 — 파일럿에서 반드시 확인할 것

holistic 단일 등급은 **중심화 경향**(3~4점에 몰림)이 있다.
현재 `grade_gap_min = 2`이므로, 단독 중앙값이 3이면 그룹이 **5점**이어야 Q3을 통과한다.
그래서 A2/A4가 전부 L2에 갇힐 가능성이 있다.

**파일럿 후 반드시 이것부터 확인한다.**

```python
import pandas as pd
grades = pd.Series([...])       # 파일럿에서 나온 모든 등급
print(grades.value_counts().sort_index())
print("표준편차:", grades.std())
```

- 등급이 2개 이하의 값에만 몰려 있거나 표준편차가 0.7 미만이면 → **척도가 작동하지 않는 것**
- 그 경우 §6의 캘리브레이션으로 `grade_gap_min`을 1로 내리거나,
  아래 **analytic 척도로 전환**한다.

<details>
<summary>대안: analytic 4차원 척도 (0~16점) — 필요해지면 여기로 전환</summary>

holistic 1개 대신 차원별로 0~4점씩 매겨 합산한다. 분산이 커져 `grade_gap`이 의미를 갖는다.

**A2 (의견수렴)**

| 차원 | 0점 | 2점 | 4점 |
|---|---|---|---|
| Coverage(포괄) | 1개 입장만 | 모든 이해관계자 언급 | 전원 언급 + 각각의 수치 요구 인용 + 미충족 항목 명시 |
| Integration(조율) | 충돌 미인지 | 충돌 인지, 임의 절충 | 충돌 명시 + 우선순위 원칙으로 해소 |
| Justification(근거) | 근거 없음 | 일반론적 근거 | 지문의 수치·제약을 인용한 검증 가능한 근거 |
| Decidability(결정성) | 결론 없음 | 결론 있으나 모호 | 단일 최종안 + 실행 가능한 형태 |

**A4 (창의공동생성)**

| 차원 | 산출 방식 |
|---|---|
| Completeness | 지문의 필수 포함 사항 N개 중 충족 수 → 0~4 매핑 |
| Feasibility | 제약 위반 건수 → 0건=4, 1건=3, 2건=2, 3건=1, 4건+=0 |
| Originality | 0=템플릿 수준 … 4=제약을 역이용한 비자명 아이디어 |
| Coherence | 세션·지표·리스크가 서로 연결되는가 |

전환 시 함께 고쳐야 하는 곳: `scoring.score_a2_a4`, `features.extract_features`(중앙값 계산),
`classify.classify`(Q3), `configs/thresholds_v*.json`(`grade_gap_min` 범위 재설정).

</details>

### 4-6. 신규 해결책 판정 (`new_idea_flag`)

L4 판정의 핵심 게이트다. 단독 산출물들에 없던 해결책 요소가 그룹 산출물에 있는지
judge가 true/false로 답한다.

**'새로운 요소'로 인정하지 않는 것** (프롬프트에 명시되어 있다):
- 표현이나 문체의 차이
- 같은 내용을 더 자세히 쓴 것
- 순서만 바꾼 것
- 단독 산출물 A의 요소와 B의 요소를 **단순히 나란히 붙인 것**

**인정하는 것**: 단독 산출물 어디에도 없던 판단 기준, 절차, 대안이 새로 등장한 경우.
확신이 서지 않으면 `false`.

## 5. 정량 지표

태깅이 끝난 로그에서 계산한다. 구현: `features.extract_features()`

| 지표 | 정의 | 쓰이는 곳 |
|---|---|---|
| `dir_AB` | alpha가 beta의 발화 **내용을 받아** 말한 턴 수 | Q1, Q2 |
| `dir_BA` | beta가 alpha의 발화 내용을 받아 말한 턴 수 | Q1, Q2 |
| `comp_ratio` | `comp` 코드가 붙은 턴 수 ÷ 전체 턴 수 | Q4a |
| `revision_seq` | `agree` 코드 + 참조가 있는 턴 수 | Q4c |
| `solo_p90` | 단독 조건 점수 분포의 90퍼센타일 (A1) | Q3 |
| `solo_median_grade` | 단독 조건 등급의 중앙값 (A2/A4) | Q3 |
| `new_idea_flag` | 신규 해결책 존재 여부 | Q4b |

### 결정 트리

```
Q1  참조가 하나라도 있는가?              아니오 → L0
      ↓ 예
Q2  양방향 모두 bidirectional_min 이상?   아니오 → L1
      ↓ 예
Q3  집단이 단독보다 나은가?               아니오 → L2
      A1   : group_score > solo_p90
      A2/A4: group_grade - solo_median_grade >= grade_gap_min
      ↓ 예
Q4  다음 셋을 모두 만족?                  아니오 → L3
      a) comp_ratio   >= comp_ratio_min
      b) new_idea_flag == True
      c) revision_seq >= revision_seq_min
      ↓ 예
    L4
```

> Q3의 부등호가 A1은 `>`(엄격), A2/A4는 `>=`(비엄격)인 이유:
> A1은 "단독 상위 90%를 **넘어야** 한다"는 퍼센타일 비교이고,
> A2/A4는 "등급차가 기준**만큼은** 되어야 한다"는 차이 비교라 성격이 다르다.

### 현재 임계값 (v1 — 근거 없는 가설값)

`configs/thresholds_v1.json`

| 키 | 값 | 뜻 |
|---|---|---|
| `bidirectional_min` | 2 | Q2: 방향별 최소 참조 턴 수 |
| `solo_percentile_A1` | 90 | Q3(A1): 단독 분포의 몇 퍼센타일 |
| `grade_gap_min` | 2 | Q3(A2/A4): 최소 등급차 |
| `comp_ratio_min` | 0.15 | Q4a |
| `revision_seq_min` | 1 | Q4c |

> ⚠️ **v1 값으로 나온 결과를 최종 결과로 보고하지 말 것.** 전부 파일럿 전 추측값이다.
> §6의 절차로 v2를 만든 뒤에 본실험을 돌린다.

## 6. 임계값 캘리브레이션 절차

"왜 이 숫자인가"에 답하기 위한 절차다. **이 절차를 거치지 않은 임계값은 근거가 없다.**

### 6-1. 파일럿 데이터 수집

| 조건 | 규모 | 근거 |
|---|---|---|
| dyad | 시나리오 7 × 조건 2 × rep 3 = **42** | 각 셀에 최소 3개는 있어야 우연을 걸러낸다 |
| solo | 시나리오 7 × 에이전트 2 × rep 5 = **70** | A1의 `solo_p90`이 안정되려면 시나리오당 최소 10개 |

**단독 표본 수가 결정적이다.** n이 작으면 p90이 사실상 최댓값이 되어 그룹이 이길 수 없다.

| n | p90의 위치 |
|---|---|
| 3 | 상위 2개 사이 (거의 최댓값) |
| 5 | 인덱스 3.6 지점 — **최댓값의 90~95% 수준** |
| 10 | 인덱스 8.1 지점 — 비로소 '상위권'다워진다 |

→ `n_solo=5`(에이전트당) = **시나리오당 10개**를 최소선으로 삼는다.

### 6-2. 인간 정답 라벨 만들기

1. 42개 중 **최소 21개**(50%)를 뽑는다. 시나리오 유형과 조건이 골고루 섞이게 뽑는다.
2. 팀원 **2인이 독립적으로** L0~L4를 판정한다.
   - 자동 판정 결과를 **보지 않고** 한다.
   - §5의 층위 정의와 로그(turns + 산출물)만 보고 판단한다.
3. 두 사람의 일치도(Cohen's κ)를 먼저 계산한다.
   - κ < 0.6이면 **사람끼리도 기준이 안 맞는 것**이다. 층위 정의를 다듬고 다시 한다.
   - 자동 판정을 사람과 비교하는 건 그 다음이다.
4. 불일치 건은 토론으로 합의해 **정답 라벨(consensus label)**을 만든다.

### 6-3. 격자 탐색

저장된 로그를 재판정하는 것이므로 **API 비용이 0이다.** 마음껏 돌린다.

```python
from itertools import product
from coop_pipeline.runner import classify_saved_log
from coop_pipeline import load_thresholds
from pathlib import Path

human_labels = {"A1_simple_meeting_명시_1": "L3", ...}   # 6-2에서 만든 정답

grid = product(
    [1, 2, 3],                    # bidirectional_min
    [1, 2, 3, 4],                 # grade_gap_min

    [1, 2],                       # revision_seq_min
)

rows = []
for bmin, gap, comp, rev in grid:
    th = dict(base, bidirectional_min=bmin, grade_gap_min=gap,

    for p in log_paths:
        if p.stem not in human_labels:
            continue
        pred.append(classify_saved_log(p, th, verbose=False)["level"])
        true.append(human_labels[p.stem])
    rows.append({"bmin": bmin, "gap": gap, "comp": comp, "rev": rev,

import pandas as pd
```

### 6-4. 선택 기준

**quadratic weighted Cohen's κ를 최대화**하는 조합을 고른다.

L0~L4는 **순서형**이다. L4를 L3로 틀린 것과 L4를 L0로 틀린 것은 심각도가 다른데,
일반(unweighted) κ는 둘을 똑같이 취급한다. 반드시 weighted를 쓴다.

```python
from sklearn.metrics import cohen_kappa_score

LEVELS = ["L0", "L1", "L2", "L3", "L4"]

def weighted_kappa(true, pred):
    to_int = {lv: i for i, lv in enumerate(LEVELS)}
    return cohen_kappa_score([to_int[t] for t in true],
                             [to_int[p] for p in pred],
                             weights="quadratic")
```

동률이면 **더 보수적인(임계가 높은) 조합**을 고른다. 협력을 과대 판정하는 쪽이
과소 판정하는 쪽보다 주장이 약해지기 때문이다.

### 6-6. 함께 보고할 신뢰도 3종

| 지표 | 무엇의 신뢰도 | 계산 방법 |
|---|---|---|

### 7-1. A1 채점

| 한계 | 내용 | 대응 |
|---|---|---|
| 의미 등가 미인식 | `"19:00"`은 잡지만 `"오후 7시"`는 못 잡는다 | 파일럿에서 발생 빈도를 세고, 잦으면 체크리스트에 대안 표기를 추가 |
| 오답 무감점 | 정답과 오답을 함께 나열하면 만점 | 양다리 답변의 빈도를 수동으로 세어 보고 |
| 토큰 부분 일치 | `"과부하"` 한 단어만 맞아도 항목의 1/5점 | `partial=False`로 재채점해 결과가 뒤집히는지 확인(민감도 분석) |

### 7-2. A2/A4 채점

- 중심화 경향 (§4-5). 파일럿에서 등급 분포를 반드시 확인.
- judge 1회 호출이라 채점 재현성이 측정되지 않는다.
  → 파일럿에서는 산출물 일부를 **3회 반복 채점**해 일치율을 보고할 것.

### 7-3. 정량 지표

| 한계 | 내용 |
|---|---|
| `revision_seq`의 이름 | '연속 시퀀스'가 아니라 `agree`+참조 **턴 개수**다. 실제 계획 수정 횟수의 근사값 |
| 참조 탐지 범위 | 태깅 시 직전 2턴만 본다. 여러 턴 전 제안을 뒤늦게 반영하면 참조로 안 잡힌다 |
| 첫 턴의 구조적 제약 | 대화 첫 발화는 참조할 대상이 없다. `max_turns=10`이면 `dir_AB`의 최대치는 4 |
| 턴 수 고정 | 3턴에 합의해도 10턴을 채운다. 뒤쪽 턴이 `phatic`으로 채워져 `comp_ratio`가 희석된다 |

**`context_window`와 `max_turns`는 파일럿과 본실험에서 같은 값을 써야 한다.**
바뀌면 캘리브레이션한 임계값이 무효가 된다.

### 7-4. 시나리오 설계

- 현재 A4 시나리오 3개는 모두 `shared`(양쪽 동일 지문)를 쓴다.
  [scenarios/README.md](../scenarios/README.md)는 A4에 **비대칭 창작 제약**을 권장하는데,
  실제 파일은 그렇지 않다. 동일 지문에서는 서로 보완할 구조적 이유가 없어
  `comp` 발화가 적게 나올 수 있다.
  → 파일럿에서 A4의 `comp_ratio`가 유독 낮으면 이것이 원인이다.
  → 코드는 이미 `alpha`/`beta` 키를 지원하므로, **시나리오 JSON에 키를 추가하기만 하면 된다.**
