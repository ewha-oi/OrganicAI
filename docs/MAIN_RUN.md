**9번 (경로 점검)** — 통과 기준은 하나뿐이다: **에러 없이 `L0`~`L4` 중 하나가 나오는 것.** 층위가 낮게 나오거나 병목이 `Q3`로 찍히는 건 정상이다(`n_solo=2, max_turns=6` 축소 설정이라 그렇다). 이건 실험 결과지 형식 오류가 아니다.

## 4. 담당자별 시나리오 교체

**고치는 셀은 하나뿐이다.** 첫 줄이 이것인 셀:

```
# 담당자가 고치는 셀은 여기 하나뿐이다 — 아래 셀들은 그대로 둔다.
```

이 셀의 `SCENARIOS = [ ... ]` **대괄호 안 목록만 통째로 바꾼다.** 나머지 값
(`MY_REPS`, `MAX_TURNS`, `N_SOLO`, `BATCH`, `OUT_DIR`)은 **건드리지 않는다** — 세 사람이
같은 값을 써야 한다.

### 기본값 = 김유리 담당 16개

지금의 셀은 내(김유리의) 담당 시나리오를 기준으로 작성되어 있다.

### 나머지 15개 (다른 담당자용)

아래를 그대로 복사해 `SCENARIOS = [` 와 `]` 사이에 **덮어쓴다.**

```python
    "scenarios/A1/A1_complex_library_leak.json",
    "scenarios/A1/A1_complex_server_temp.json",
    "scenarios/A1/A1_simple_lab_meeting.json",
    "scenarios/A1/A1_simple_printer.json",
    "scenarios/A1/A1_simple_study_room.json",
    "scenarios/A2/A2_complex_event_budget.json",
    "scenarios/A2/A2_complex_lab_space.json",
    "scenarios/A2/A2_simple_lecture_day.json",
    "scenarios/A2/A2_simple_snack_vendor.json",
    "scenarios/A2/A2_simple_tshirt_vendor.json",
    "scenarios/A4/A4_complex_mentoring.json",
    "scenarios/A4/A4_complex_project_kickoff.json",
    "scenarios/A4/A4_simple_energy_save.json",
    "scenarios/A4/A4_simple_library_quiet.json",
    "scenarios/A4/A4_simple_recycling.json",
```

### 왜 rep은 안 나누는가

로그 파일명이 `{scenario_id}_{condition}_{rep}.json`이다. **담당 시나리오가 서로 겹치지
않으면 rep이 같아도 파일명이 절대 겹치지 않는다.** 그래서 시나리오로 분담하는 지금은
전원 `MY_REPS = range(1, 10)`을 그대로 쓴다.

> `README.md`의 rep 분배표(김유리 1~5 / 이예영 6~10 / 김유민 11~15)는 **시나리오를
> 나누지 않고 전원이 같은 시나리오를 돌리던 방식**의 규칙이다. 지금 단계에는 적용하지
> 않는다. 두 방식을 섞으면 내 시나리오는 rep 1~5만, 남의 시나리오는 rep 6~10만 존재하게
> 되어 시나리오마다 rep 번호가 달라진다.

### 충돌 확인

돌리기 전에 목록이 겹치지 않는지 한 번만 맞춰본다. 겹치면 **나중에 돌린 사람이 앞 사람
파일을 조용히 덮어쓴다** (파일명에 사람 구분이 없다).

## 5. 한 번 실행하면 얼마나 도는가

**`BATCH = 16` → 담당 시나리오 전체 × rep 한 바퀴 × 명시/묵시 두 조건.** 약 1.5~2시간.

```
1회차 실행 → 담당 16개 × rep 1
2회차 실행 → 담당 16개 × rep 2
...
```

`MY_REPS = range(1, 10)`이라 최대 rep 9까지 계획돼 있다. **한 번에 다 돌리는 것이
아니라, 하루 한 배치씩 나눠 돌린다.** Groq 무료 티어 일일 한도(특히 judge) 때문이다.

| 범위 | 총 호출 | judge 몫 |
|---|---|---|
| 1배치 (16개 × rep 1) | 약 1,100회 | 약 590회 |

도중에 멈춰도 **그때까지 모인 것이 유효한 데이터다.** rep을 바깥 루프에 두었기 때문에
시나리오별 rep 수가 항상 고르게 유지된다.

### 이어서 돌리기 · 실패 처리

수집 셀은 그냥 **다시 실행하면 된다.**

- 명시·묵시가 다 저장된 `(시나리오, rep)`은 자동으로 건너뛴다
- 한 건이 실패해도 루프가 멈추지 않고, 끝에 실패 목록을 찍는다
- 실패분은 다시 실행할 때 재시도된다

## 6. 데이터는 어디에 쌓이나

`/content/drive/MyDrive/OrganicAI_main` — **세 사람이 같은 폴더를 쓴다.** 파일럿 로그와
섞이면 안 되므로 본실험은 별도 폴더다.

저장은 루프 끝이 아니라 **각 단계 직후**에 일어난다.

```
대화 10턴 실행  ──→ 즉시 raw/ 에 저장   ← 여기서 끊겨도 대화는 남는다
태깅 → 채점 → 판정 ──→ 완성본 저장
```

`raw/`에 먼저 쓰는 것은 대화가 가장 비싼 단계라 뒤에서 실패해도 잃지 않기 위해서다.

```
OrganicAI_main/
├── raw/                                   ← 태깅 전 원본
│   ├── A1_complex_gas_alarm_명시_1.json
│   └── A1_complex_gas_alarm_묵시_1.json
├── A1_complex_gas_alarm_명시_1.json        ← 완성본 (판정까지)
└── A1_complex_gas_alarm_묵시_1.json
```

시나리오 1개 × rep 1회 = **파일 4개**.

특히 **judge가 다르면 태깅이 달라져 Kappa 비교가 무효가 된다.**

### 임계값은 동결 대상이 아니다

저장되는 것은 로그(발화 · 태그 · 점수)이고 **판정은 읽을 때 계산된다.** 그래서 수집이
끝난 뒤 `classify_saved_dir()`로 임계값을 바꿔가며 **무료로 몇 번이든 다시 판정할 수
있다.** 지금 임계값 때문에 수집을 미룰 이유가 없다.

다만 결과를 보고 기준을 고르면 "협력 효과가 있었다"가 아니라 "기준을 낮췄다"가 된다.
확정 절차는 [RUBRIC.md](RUBRIC.md)의 「임계값 캘리브레이션」을 따른다.

## 8. 자주 나는 에러

| 증상 | 원인 | 해결 |
|---|---|---|
| alpha 호출이 전부 `404` | shim 셀을 안 돌림 | `# alpha 대체 어댑터...` 셀 실행 |
| `NameError: SCENARIOS` | 설정 셀을 안 돌림 | 1절 설정 셀부터 다시 |
| `429` / rate limit | 일일·분당 한도 | shim 셀의 `RATE_LIMIT_SLEEP`을 6.0~10.0으로. 그래도 나면 다음 날 |
| `not_found_error` 404 | 모델 퇴역 | 부록 모델 목록 셀 → `MODEL_ASSIGNMENT.md` 재배정 절차 |
| `judge 제공사가 'groq'인데 api_keys['groq']가 비어 있음` | Secrets 미등록 | 키 셀에서 `groq OK` 확인 |
| `alpha(...) 빈 응답` | 추론 토큰 소진 | shim 셀 재실행 (`EXTRA` 옵션 재탐색) |
| 코드를 고쳤는데 반영이 안 됨 | 런타임 재시작 안 함 | `git pull` → **런타임 재시작** → 1절부터 |
