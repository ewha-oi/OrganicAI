## 4. 담당자별 시나리오 교체

**고치는 셀은 하나뿐이다.** 첫 줄이 이것인 셀:

```
# 담당자가 고치는 셀은 여기 하나뿐이다 — 아래 셀들은 그대로 둔다.
```

이 셀의 `SCENARIOS = [ ... ]` **대괄호 안 목록만 통째로 바꾼다.** 나머지 값
(`MY_REPS`, `MAX_TURNS`, `N_SOLO`, `BATCH`, `OUT_DIR`)은 **건드리지 않는다** — 세 사람이
같은 값을 써야 한다.

### 기본값 = 김유리 담당 16개

지금의 셀은 내(김유리의) 담당 시나리오를 기준으로 작성되어 있다.

### 나머지 15개 (다른 담당자용)

아래를 그대로 복사해 `SCENARIOS = [` 와 `]` 사이에 **덮어쓴다.**

```python
    "scenarios/A1/A1_complex_library_leak.json",
    "scenarios/A1/A1_complex_server_temp.json",
    "scenarios/A1/A1_simple_lab_meeting.json",
    "scenarios/A1/A1_simple_printer.json",
    "scenarios/A1/A1_simple_study_room.json",
    "scenarios/A2/A2_complex_event_budget.json",
    "scenarios/A2/A2_complex_lab_space.json",
    "scenarios/A2/A2_simple_lecture_day.json",
    "scenarios/A2/A2_simple_snack_vendor.json",
    "scenarios/A2/A2_simple_tshirt_vendor.json",
    "scenarios/A4/A4_complex_mentoring.json",
    "scenarios/A4/A4_complex_project_kickoff.json",
    "scenarios/A4/A4_simple_energy_save.json",
    "scenarios/A4/A4_simple_library_quiet.json",
    "scenarios/A4/A4_simple_recycling.json",
```

### 왜 rep은 안 나누는가

로그 파일명이 `{scenario_id}_{condition}_{rep}.json`이다. **담당 시나리오가 서로 겹치지
않으면 rep이 같아도 파일명이 절대 겹치지 않는다.** 그래서 시나리오로 분담하는 지금은
전원 `MY_REPS = range(1, 10)`을 그대로 쓴다.

> `README.md`의 rep 분배표(김유리 1~5 / 이예영 6~10 / 김유민 11~15)는 **시나리오를
> 나누지 않고 전원이 같은 시나리오를 돌리던 방식**의 규칙이다. 지금 단계에는 적용하지
> 않는다. 두 방식을 섞으면 내 시나리오는 rep 1~5만, 남의 시나리오는 rep 6~10만 존재하게
> 되어 시나리오마다 rep 번호가 달라진다.

### 충돌 확인

돌리기 전에 목록이 겹치지 않는지 한 번만 맞춰본다. 겹치면 **나중에 돌린 사람이 앞 사람
파일을 조용히 덮어쓴다** (파일명에 사람 구분이 없다).

## 5. 한 번 실행하면 얼마나 도는가

**`BATCH = 16` → 담당 시나리오 전체 × rep 한 바퀴 × 명시/묵시 두 조건.**

소요 시간은 **요청 수가 아니라 분당 토큰 한도(TPM)가 정한다.** §9를 먼저 읽고,
첫 배치를 돌려 실제 걸린 시간을 재본 뒤에 계획을 세울 것. 무료 티어에서는
한 배치에 **반나절 이상** 걸릴 수 있다.

```
1회차 실행 → 담당 16개 × rep 1
2회차 실행 → 담당 16개 × rep 2
...
```

`MY_REPS = range(1, 10)`이라 최대 rep 9까지 계획돼 있다. **한 번에 다 돌리는 것이
아니라, 하루 한 배치씩 나눠 돌린다.** Groq 무료 티어 일일 한도(특히 judge) 때문이다.

| 범위 | 총 호출 | judge 몫 |
|---|---|---|
| 1배치 (16개 × rep 1) | 약 1,100회 | 약 590회 |

> 이 표는 **호출 수**다. 실제 병목은 토큰이다 — §9.

도중에 멈춰도 **그때까지 모인 것이 유효한 데이터다.** rep을 바깥 루프에 두었기 때문에
시나리오별 rep 수가 항상 고르게 유지된다.

### 이어서 돌리기 · 실패 처리

수집 셀은 그냥 **다시 실행하면 된다.**

- 명시·묵시가 다 저장된 `(시나리오, rep)`은 자동으로 건너뛴다
- 한 건이 실패해도 루프가 멈추지 않고, 끝에 실패 목록을 찍는다
- 실패분은 다시 실행할 때 재시도된다

## 6. 데이터는 어디에 쌓이나

팀 공유 폴더 **「유기농지능 > data」** 에 쌓인다. Colab 경로로는
`/content/drive/MyDrive/유기농지능/data`.

- **세 사람이 같은 폴더를 쓴다.** 그래야 현황 확인 셀에서 전체가 한 번에 보인다
- **폴더를 손으로 만들 필요는 없다.** 수집 셀이 없으면 알아서 만든다
- 담당 시나리오가 겹치지 않으면 파일명도 겹치지 않으므로, 같은 폴더에 쌓아도 안전하다

저장은 루프 끝이 아니라 **각 단계 직후**에 일어난다.

```
대화 10턴 실행  ──→ 즉시 raw/ 에 저장   ← 여기서 끊겨도 대화는 남는다
태깅 → 채점 → 판정 ──→ 완성본 저장
```

`raw/`에 먼저 쓰는 것은 대화가 가장 비싼 단계라 뒤에서 실패해도 잃지 않기 위해서다.

```
유기농지능/
└── data/
    ├── raw/                                   ← 태깅 전 원본
    │   ├── A1_complex_gas_alarm_명시_1.json
    │   └── A1_complex_gas_alarm_묵시_1.json
    ├── A1_complex_gas_alarm_명시_1.json        ← 완성본 (판정까지)
    └── A1_complex_gas_alarm_묵시_1.json
```

시나리오 1개 × rep 1회 = **파일 4개**.

> `data` 폴더에 파일럿 때 모은 로그가 이미 있다면, 파일명 규칙
> (`{scenario_id}_{condition}_{rep}.json`)이 같아서 현황 확인 셀에 함께 잡힌다.
> 본실험 것과 구분해야 하면 파일럿 로그를 하위 폴더로 옮겨두고 시작할 것.

## 9. TPM — 실제 병목

Groq 무료 티어는 **분당 토큰 수(TPM)** 로 막힌다. 그리고 요청 하나의 비용을 이렇게 센다.

```
요청 비용 = 프롬프트 토큰 + max_tokens
```

`max_tokens`는 **실제로 쓴 양이 아니라 예약량**이다. 400자만 답해도 `max_tokens=4096`을
걸었으면 4096을 다 청구한다.

문제는 대화가 진행될수록 프롬프트가 커진다는 것이다. `agents.run_dyad`는 매 턴 **지금까지의
대화 전체**를 프롬프트에 넣는다. 그래서 턴이 쌓이면 어느 순간 한도를 넘는다.

```
1턴  : 프롬프트 1,200 + 예약 2,048 = 3,248   OK
6턴  : 프롬프트 4,959 + 예약 4,096 = 9,055   413 (한도 8,000)
10턴 : 더 커진다
```

**기다려도 풀리지 않는다.** 429(분당 요청 수 초과)와 달리 413은 "요청 하나가 한도보다
크다"는 뜻이라, 재시도해도 같은 크기면 계속 실패한다.

### 지금 코드가 하는 대응

shim 셀이 `ALPHA_MAX_TOKENS = 2048`에서 시작해, 413이 나면 **절반씩 낮춰 재시도**한다
(`768`이 하한). 낮출 때마다 이렇게 찍힌다.

```
  ! TPM 초과 — max_tokens=1024 로 낮춰 재시도
```

`768`까지 낮췄는데도 413이면 **프롬프트 자체가 한도보다 큰 것**이라 `max_tokens`로는
해결되지 않는다. 그때는 아래 중 하나를 선택해야 한다.

### 해결한 방법 — 발언 길이 제한

`MAX_TURNS`도 모델도 건드리지 않고, **대화 중 발언을 짧게** 해서 해결했다
([agents.py:32](../src/coop_pipeline/agents.py:32) `SYSTEM_PROMPT_TEMPLATES`).

```
대화 중 각 발언은 5문장 이내의 줄글로 하라. 표·제목·번호 목록 같은 문서 형식은
쓰지 말고, 핵심만 말하라. (최종 결론을 작성할 때는 이 길이 제한을 적용하지 않는다.)
```

- 명시·묵시 **양쪽에 똑같이** 붙는다. 조건 간 차이는 여전히 `협력하여 함께` 두 단어뿐이다
- 마무리(`FINALIZE_PROMPT`)에는 적용되지 않는다 — `final_output`이 채점 대상이므로
  거기서는 형식을 갖춘 긴 산출물이 나와야 한다
- 단독 조건(`run_solo`)은 이 템플릿을 쓰지 않으므로 **Q3의 기준선은 그대로다**

턴당 이력 증가가 941토큰 → 200~350토큰으로 줄어 10턴이 한도 안에 들어온다.
실제로 들어왔는지는 사전 점검 `[4]` 셀이 확인해 준다.

## 10. TPD — 진짜 상한

TPM보다 **judge의 일일 토큰 한도(TPD)** 가 먼저 막는다.

```
qwen/qwen3.6-27b — tokens per day (TPD): Limit 200,000
```

judge는 태깅·채점·신규성 판정을 전부 맡아서 호출이 가장 많다. 그래서 수집 속도는
사실상 이 값이 정한다.

### 낭비를 먼저 제거했다

제공사는 `max_tokens`를 **예약량으로 미리 청구한다.** 수십 토큰짜리 JSON을 받으면서
4,096을 매번 다 내고 있었다.

| 고친 것 | 효과 |
|---|---|
| `_MIN_OUTPUT_TOKENS` 4096 → 1024 ([llm.py:162](../src/coop_pipeline/llm.py:162)) | 호출당 5,201 → 2,129토큰 |
| 단독 산출물 재채점 제거 ([runner.py:177](../src/coop_pipeline/runner.py:177)) | A2/A4 시나리오당 judge 10회 절약 |

두 번째는 비용 문제만이 아니었다. 명시·묵시가 같은 단독 산출물을 **조건마다 다시
채점**하고 있어서, 같은 글에 다른 등급이 나올 수 있었다. 이제 한 번 채점해 양쪽이
그대로 쓰므로 "두 조건이 같은 기준선을 쓴다"는 전제가 실제로 성립한다.

```
A2/A4 시나리오 1개(양 조건)  44회 × 5,201 = 229k  →  34회 × 2,129 = 72k
```

### 그래도 남는 제약

| | 하루 가능량 |
|---|---|
| A1 시나리오 | 약 4개 |
| A2/A4 시나리오 | 약 2~3개 |

담당 16개를 **rep 한 바퀴 도는 데 약 5~6일**이다. `MY_REPS = range(1, 4)`(3회)로
잡아둔 것이 이 때문이다. 더 늘리려면 아래를 팀이 정해야 한다.

| 방법 | 대가 |
|---|---|
| **Dev 티어 결제** | 비용. 설계를 안 건드린다 |
| **rep을 더 줄인다** | 통계적 검정력 |
| **judge를 다른 제공사로** | alpha·beta가 gpt 계열이므로 Gemini judge는 계열이 겹치지 않는다 — 원래 걱정하던 self-preference 편향이 지금 구성에선 해당 없음 |

> 새 API 키를 발급받는 것은 해결이 아니다. 한도는 **조직 단위**라 같은 계정의 새 키는
> 같은 한도를 쓴다. 계정을 새로 만드는 것은 제공사 약관 위반이다.

### 한도에 걸렸을 때

```
RateLimitError: 429 ... tokens per day (TPD): Limit 200000, Used 196693
```

기다리면 리셋된다. 수집 셀은 **이어서 돌리기**가 되므로, 다음 날 그대로 다시 실행하면
남은 것부터 이어간다. 이미 저장된 로그는 손상되지 않는다.

**사전 점검을 반복해서 돌리면 한도가 금방 닳는다.** 경로 점검 1회가 약 161k,
태깅 점검 1회가 약 26k다. 첫날 한 번씩만 돌릴 것.

`MODEL_ASSIGNMENT.md` §2도 TPM을 두고 "`max_turns` 상한을 사실상 이것이 정한다"고 적어
두었다. 이번 413이 그 경고가 실제로 걸린 것이다.

### 시작 전에 실제 한도 확인하기

shim 셀 끝에서 현재 alpha의 TPM 한도와 1턴 프롬프트 크기를 찍는다.

```
TPM 한도        : 8000
1턴 프롬프트    : 1183 토큰
요청당 비용     : 프롬프트 + max_tokens(2048) = 3231
프롬프트 여유   : 5952 토큰까지 (이걸 넘으면 413)
```

`!! 1턴부터 한도의 절반을 넘게 쓴다` 경고가 뜨면 `max_turns=10`은 중간에 막힐 가능성이
높다. 수집을 시작하기 전에 팀과 상의할 것.

세 모델(alpha·beta·judge)의 TPM·RPD를 한 번에 보려면
[MODEL_ASSIGNMENT.md](MODEL_ASSIGNMENT.md) §4 `[0]` 프로브 셀을 돌린다.
