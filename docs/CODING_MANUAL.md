# 발화 태깅 코딩 매뉴얼 (v2)

대화 로그의 각 발화(turn)에 **협력 발화 코드**와 **참조 방향**을 붙이는 기준이다.

이 문서는 두 가지 용도로 쓴다.

1. **인간 코더**가 읽고 직접 태깅할 때의 기준
2. **LLM 코더**에게 주는 프롬프트(`tagging.py`의 `CODING_MANUAL`)의 원본

> ⚠️ 둘은 **반드시 같은 내용**이어야 한다. 어긋나면 인간과 LLM의 Cohen's κ가 낮게 나오는데,
> 그것이 코더 문제인지 매뉴얼 불일치 때문인지 구별할 수 없게 된다.
> 기준을 바꿀 때는 **이 문서와 `tagging.py`를 함께** 고친다.

---

## 1. 코드 6종

| 코드 | 정의 |
|---|---|
| `phatic` | 사교적/대화 유지용 발화. 과제 내용이 없음 |
| `meta` | 협력 과정 자체를 언급. 진행 방식·역할·순서에 대한 발화 |
| `lead` | 논의의 초점이나 다음 할 일을 지정 |
| `arch` | 대화에 아직 등장하지 않은 정보·주장·아이디어를 새로 제시 |
| `agree` | 상대 발화를 받아들여 **자신의 이전 입장이나 계획을 바꿈** |
| `comp` | 상대가 요청하지 않았는데 상대 발화의 **빠진 부분을 자발적으로 메움** |

한 발화에 여러 코드를 붙일 수 있다. 해당 없으면 빈 배열 `[]`.

---

## 2. 판정 규칙 (반드시 지킬 것)

이 5개 규칙이 매뉴얼의 핵심이다. 정의만으로는 코더마다 다르게 판단한다.

### R1. `phatic`은 잔여 범주다

다른 코드가 **하나라도** 붙으면 `phatic`을 붙이지 않는다.

### R2. `agree`는 두 조건을 모두 만족해야 한다

- (a) 상대 의견을 수용하는 표현이 있고
- (b) 자신이 앞서 말한 내용을 **철회·수정·보강**하는 진술이 있다

**수용 표현만 있고 자기 입장 변경이 없으면 `agree`가 아니라 `phatic`이다.**

### R3. `comp`는 두 조건을 모두 만족해야 한다

- (a) 상대가 **명시적으로 요청하지 않았고**
- (b) 상대 발화에 **빠져 있던 요소를 채운다**

상대의 질문에 대한 단순 답변은 `comp`가 아니다.

### R4. `arch`는 처음 등장하는 내용이어야 한다

앞서 나온 내용의 반복·재진술은 `arch`가 아니다.

### R5. 참조(ref)는 상대 발화의 **내용**을 받아야 한다

- 상대 이름을 부르기만 한 것("beta야, 내 생각엔")은 참조가 **아니다**
- 상대가 말한 사실·제안·질문을 언급하거나 답할 때만 참조다
- **자기 자신은 절대 참조 대상이 될 수 없다** (코드에서도 막힌다)

## 3. 경계 사례 — 헷갈리는 쌍

### 3-1. `agree` vs `phatic` ★ 가장 중요

| 발화 | 코드 | 이유 |
|---|---|---|
| "좋아, 그렇게 하자." | `phatic` | 수용 표현만 있고 자기 입장 변경이 없음 (R2-b 미충족) |
| "맞네, 나는 A실을 생각했는데 수요일이면 B실이 맞겠다." | `agree` | 수용 + **자기 이전 안(A실)을 철회** |
| "알겠어. 그럼 다음 얘기 하자." | `phatic` | 과제 내용 없음 |
| "네 말이 맞아. 그러면 예산 항목을 60에서 70으로 올릴게." | `agree` | 수용 + 자기 계획 수정 |

> `comp_ratio`와 `revision_seq`가 이 구분에 달려 있다. 여기서 흔들리면 L3/L4 판정이 흔들리게 된다.

### 3-2. `comp` vs 단순 답변

| 발화 | 코드 | 이유 |
|---|---|---|
| (상대: "요일은 언제로 할까?") "수요일이 좋겠어." | `arch` | 요청받은 답변. `comp` 아님 (R3-a 미충족) |
| (상대: "수요일 B실로 하자.") "좋아. 그런데 예산 확인도 필요해 보여." | `comp` | 요청받지 않았는데 상대가 빠뜨린 요소를 채움 |
| (상대: "예산은 200이야.") "응, 200이지." | `phatic` | 반복. 새 정보도 보완도 아님 |

### 3-3. `arch` vs 반복

| 발화 | 코드 | 이유 |
|---|---|---|
| (1턴) "A실은 화/목만 열려." | `arch` | 첫 등장 |
| (5턴) "아까 말했듯 A실은 화/목만 열려." | (없음) | 재진술. R4 위반 |
| (5턴) "A실은 화/목만 열리고, 게다가 대관료가 있어." | `arch` | 대관료는 새 정보 |

### 3-4. `meta` vs `lead`

| 발화 | 코드 | 이유 |
|---|---|---|
| "우리 지금 방향이 엇갈리는 것 같아, 다시 정리하자." | `meta` | **협력 과정 자체**를 언급 |
| "지금 정할 건 요일이야. 시간은 나중에." | `lead` | 논의의 **초점**을 지정 |
| "네가 예산을 맡고 내가 일정을 볼까?" | `meta` | 역할 분담 = 과정 |

## 4. 근거(evidence) 기록

붙인 코드마다 **그 판단의 근거가 된 원문 구절을 그대로 인용**한다.

```json
{
  "codes": ["agree", "comp"],
  "reference": "alpha",
  "evidence": {
    "agree": "나는 A실을 생각했는데 수요일이면 B실이 맞겠다",
    "comp":  "그런데 예산 확인도 필요해 보여"
  }
}
```

**왜 필요한가.** 인간 코더와 LLM 코더의 결과가 갈렸을 때, 근거가 없으면
"왜 갈렸는지"를 알 수 없어 매뉴얼을 개선할 방법이 없다. κ가 낮아도 고칠 수가 없다.

## 5. 인간 코딩 절차

파일럿에서 Cohen's κ를 계산하기 위한 절차다.

1. 42개 dyad 로그 중 **최소 21개**(50%)를 뽑는다. 시나리오 유형과 조건이 골고루 섞이게.
2. 팀원 **2인이 독립적으로** 태깅한다. **LLM 태깅 결과를 보지 않는다.**
3. 각 발화에 대해 6개 코드 각각을 `있음/없음`으로 기록하고, `ref`도 기록한다.
4. 코드별로 κ를 따로 계산한다.

```python
from sklearn.metrics import cohen_kappa_score

CODES = ["phatic", "meta", "lead", "arch", "agree", "comp"]

def kappa_by_code(coder_a_turns, coder_b_turns):
    """각 turn의 codes 리스트를 받아 코드별 kappa를 계산한다."""
    result = {}
    for code in CODES:
        a = [1 if code in t["codes"] else 0 for t in coder_a_turns]
        b = [1 if code in t["codes"] else 0 for t in coder_b_turns]
        result[code] = cohen_kappa_score(a, b)      # 명목형이므로 unweighted
    # 참조는 별도
    a_ref = [1 if t["ref"] else 0 for t in coder_a_turns]
    b_ref = [1 if t["ref"] else 0 for t in coder_b_turns]
    result["ref"] = cohen_kappa_score(a_ref, b_ref)
    return result
```

### 해석 기준

| κ | 해석 | 조치 |
|---|---|---|
| ≥ 0.80 | 매우 좋음 | 그대로 진행 |
| 0.60 ~ 0.79 | 수용 가능 | 그대로 진행하되 리포트에 명시 |
| 0.40 ~ 0.59 | 부족 | 해당 코드의 경계 사례를 §3에 추가하고 **재코딩** |
| < 0.40 | 사용 불가 | 코드 정의 자체를 재검토 |

> `agree`와 `comp`의 κ가 특히 낮게 나올 가능성이 높다. R2/R3의 두 조건 규칙이
> 실제로 지켜졌는지 `evidence`를 보고 확인한다.

### 인간 vs LLM 비교

인간 2인의 κ를 먼저 확인한다. **사람끼리도 κ < 0.6이면 매뉴얼 문제**이지
LLM 코더 문제가 아니다. 매뉴얼을 먼저 고친다.

사람끼리 κ가 충분하면, 인간 합의 라벨과 LLM 코더를 같은 방식으로 비교한다.

## 6. LLM 코더 설정

| 항목 | 값 | 이유 |
|---|---|---|
| 모델 | `llm.MODELS["judge"]` (claude 계열) | 생성 모델(gemini/llama)과 분리해 편향 회피 |
| temperature | `0` | 태깅은 재현 가능해야 함 |
| `context_window` | `2` | 자기 직전 발화 + 상대 직전 발화 |
| 재시도 | 3회 | JSON 형식 오류로 배치가 죽는 것을 방지 |

**`context_window`를 바꾸면 `dir_AB`/`dir_BA`가 달라지고, 캘리브레이션한 임계값이 무효가 된다.**
파일럿과 본실험에서 같은 값을 써야 한다.

태깅 결과에는 어떤 설정으로 돌렸는지가 함께 저장된다.

```python
log["tagging"]
# {"model": "claude-sonnet-5", "context_window": 2, "manual_version": "v2"}
```
