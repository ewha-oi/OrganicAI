# 시나리오 작성 가이드

시나리오는 단순 텍스트가 아니라, 에이전트에게 제공하는 지문 + 자동 채점에 필요한 데이터가 포함된 JSON 파일이므로 아래 규칙에 맞추어 작성한다.

---

## 필드 규칙

파일명 형식: `{과제유형}_{복잡도}_{시나리오명}.json` (예: `A1_simple_meeting.json`)

> ⚠️ 파일명(확장자 제외)과 JSON 내부의 `scenario_id` 값이 반드시 일치해야 한다.

| 필드 | 필수 여부 | 설명 |
|---|---|---|
| `scenario_id` | 항상 필수 | `{과제유형}_{복잡도}_{시나리오명}` 형식 (예: `A1_simple_meeting`, 이것이 파일 제목이 됨) |
| `task_type` | 항상 필수 | `"A1"`, `"A2"`, `"A4"` 중 하나 |
| `complexity` | 항상 필수 | `"simple"` 또는 `"complex"` |
| `task_variants.alpha` | A1·A4 필수 | alpha가 받는 지문 (A1은 정보 일부, A4는 창작 제약 일부) |
| `task_variants.beta` | A1·A4 필수 | beta가 받는 지문 (alpha와 겹치지 않게 작성) |
| `task_variants.shared` | A2만 필수 | alpha, beta에게 동일하게 제공하는 지문 |
| `task_variants.solo` | 항상 필수 | 단독 조건용 지문. A1·A4는 `alpha + beta`를 모두 합친 버전이어야 한다 |
| `scoring.checklist` | A1만 필수 | 정답 채점용 키워드 목록 |

---

## 과제 유형별 구성

| 과제 유형 | 지문 구조 | 채점 방식 |
|---|---|---|
| A1 (정보통합) | `alpha` + `beta` (서로 다른 정보) + `solo` (정보 통합 버전) | Checklist 기반 자동 매칭 |
| A2 (의견수렴) | `shared` + `solo` | LLM Judge 등급 (1~5점) |
| A4 (창의공동생성) | `alpha` + `beta` (서로 다른 창작 제약) + `solo` (제약 통합 버전) | LLM Judge 등급 (1~5점) |

> A2만 `shared`를 쓴다. A2는 **같은 사안을 놓고 입장을 조율**하는 과제이므로 두 에이전트가
> 동일한 지문을 받아야 성립한다. A1·A4는 비대칭이어야 서로를 참조할 이유가 생긴다.

## 작성 시 주의사항

### 1. 역할 및 성격 부여 금지

시나리오에서 에이전트의 역할이나 성격을 지정하지 않는다.

잘못된 예:
```
너는 리더야.
너는 신중한 성격이야.
```

올바른 작성:
```
alpha
beta
```

만 사용

---

### 2. 공동 목표 포함

시나리오에는 자연스럽게 공동 목표를 포함한다.

예:
```
함께 결정하라
합의하라
```

단, `system prompt`에서 협력 조건을 별도로 추가하므로 시나리오에 "협력해라"라는 문구를 반복해서 넣지 않는다.

---

### 3. A1 정보 분배 규칙

- `alpha`와 `beta`의 정보는 반드시 서로 다르게 작성한다.
- 정보가 겹치면 정보 공유 필요성이 사라져 과제 의도가 약해진다.
- `solo`는 반드시 `alpha + beta` 정보를 모두 포함해야 한다.

일부 정보만 포함하면 단독 조건에서 해결 불가능한 과제가 되어 비교가 불가능하다.

---

### 4. 제한 조건 작성 금지

시나리오에는 아래 내용을 포함하지 않는다.

```
턴 수 제한
시간 제한
```

해당 조건은 코드(`agents.py`)에서 관리하도록 한다.

---

### 5. Scoring 작성 규칙

#### A1

`scoring.checklist`는 짧고 명확한 키워드로 작성한다.

좋은 예:
```json
[
  "수요일",
  "B실",
  "19:00"
]
```

나쁜 예:
```json
[
  "10월 5일쯤 괜찮을 듯"
]
```

자동 매칭 방식이므로 길거나 모호한 문장은 인식이 어렵다.

#### A2 / A4

정답이 존재하지 않으므로 `scoring` 필드는 작성하지 않는다.

## AI로 시나리오 생성 시 유의사항
### 기본 프롬프트 구조

AI에게 시나리오 생성을 요청할 때 아래 형식을 복붙해서 사용한다.

```
아래 조건에 맞는 시나리오 JSON 파일을 작성해줘.

[조건]
- task_type: A1 (또는 A2, A4)
- complexity: simple (또는 complex)
- scenario_id: A1_simple_XXX (파일명과 일치하게)
- 역할/성격 부여 문구 사용 금지 (너는 리더야 등)
- 턴 수, 시간 제한 문구 포함 금지
- 공동 목표는 자연스럽게 포함할 것

[A1 추가 조건]
- alpha와 beta의 정보가 겹치지 않게 작성
- 두 정보를 교차해야만 발견할 수 있는 모순 또는 결론이 포함될 것
- solo는 alpha + beta 정보를 모두 포함
- scoring.checklist는 짧은 키워드로 작성 (예: "수요일", "B실")

[A2 추가 조건]
- task_variants는 shared 하나만 (alpha/beta로 나누지 말 것)
- 입장이 갈릴 수 있는 사안일 것 (정답이 하나로 정해지면 안 됨)
- scoring 필드는 작성하지 말 것
```

---

### 핵심 설계 원칙: 구조로 협력을 유도하라

#### A1 — 정보 비대칭 구조 필수

단순히 정보를 나눠주는 것으로는 부족하다. **alpha의 정보와 beta의 정보를 교차해야만 발견할 수 있는 모순이나 결론**이 있어야 한다.

잘못 설계된 예 (피할 것):
```
alpha: "용의자는 A일 것 같다."
beta:  "용의자는 B일 것 같다."
→ 두 정보를 굳이 교차하지 않아도 각자 결론을 낼 수 있음
```

잘 설계된 예:
```
alpha: "사건 당일 A는 오후 2시에 창고에 있었다."
beta:  "창고 CCTV는 오후 1~3시 사이에 오작동했다. B는 A와 함께 있었다고 진술했다."
→ 두 정보를 합쳐야 A의 알리바이가 성립하는지 판단 가능
```

---

### complexity 설계 기준

| complexity | 기준 |
|---|---|
| `simple` | 단서가 명확하고 정답 경로가 하나 |
| `complex` | 단서가 여러 개이며 의심 방향이 분산되어 있음. 단순히 정보량을 늘리는 것이 아니라, 교차 참조해야만 확인할 수 있는 모순이 포함되어야 함 |

> complex 시나리오에서 가장 의심스러운 정답이 처음부터 명확하게 드러나면 안 된다. 에이전트가 서로 정보를 교환하지 않아도 각자 결론에 도달할 수 있으면 complex 설계가 실패한 것이다.

## 작성 후 체크리스트

### 공통
- [ ] `scenario_id`가 파일명(확장자 제외)과 일치하는가?
- [ ] `task_type`이 `A1` / `A2` / `A4` 중 하나인가?
- [ ] `complexity`가 `simple` 또는 `complex`인가?
- [ ] `solo` 지문이 있는가?
- [ ] 역할/성격 부여 문구가 없는가?
- [ ] 턴 수, 시간 제한 문구가 없는가?
- [ ] 공동 목표가 자연스럽게 포함되어 있는가?

### A1 추가 확인
- [ ] `alpha`와 `beta` 정보가 겹치지 않는가?
- [ ] 두 정보를 교차해야만 발견할 수 있는 모순 또는 결론이 있는가?
- [ ] `solo`에 `alpha + beta` 정보가 모두 들어있는가?
- [ ] `complex`인 경우, 처음부터 정답이 명확하게 드러나지 않는가?
- [ ] `scoring.checklist`가 짧고 명확한 키워드로 작성되어 있는가?

### A2 추가 확인
- [ ] `shared` 지문이 있는가? (A2는 양쪽이 같은 지문을 받아야 한다)
- [ ] 정답이 하나로 정해지지 않는, 입장이 갈릴 수 있는 사안인가?
